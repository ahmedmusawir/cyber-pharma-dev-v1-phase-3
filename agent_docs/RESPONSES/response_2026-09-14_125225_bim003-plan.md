## 3. Wrappers — N = 4

Common: `language plpgsql`, `security definer`, `set search_path = ''`, `revoke execute from public, anon`, `grant execute to authenticated`. Statement 1 = membership check, fixed message `'not a member of business'`; statement 2 = one `read_page` insert with `context = {fn, args, page, limit, offset, filters}`; statement 3 = the read, always `where business_id = p_business_id` explicitly (a DEFINER bypasses RLS — the WHERE is the fence).

## 6. Risks

- **RISK-1 — FORCE RLS vs the definer's owner.** With `force row level security` and zero INSERT policy, the trigger and the wrappers can insert only if their owner (the `DB_URL` role, `postgres`) has `BYPASSRLS`. Supabase's `postgres` is documented as BYPASSRLS, but there is no in-repo evidence. **S1 step 0: `select rolbypassrls from pg_roles where rolname = current_user`, logged into the from-scratch evidence.** If false → STOP and report; every fallback costs an erratum (drop FORCE → AC-107; an INSERT policy for postgres → AC-108).
- **RISK-2** — an `audit_write()` failure blocks every write on 13 tables. That is the design (fail closed); the 320-cell matrix exercises it before the golden run.
- **RISK-3** — `actor_role` for non-PostgREST writes (seed via `pg`) falls back to `current_user` = `postgres`; the golden run excludes them by watermark.
