## a. Keyboard/focus design (S1)

### DataTable (`src/components/common/DataTable.tsx:70-86`): button inside the `<th>`

- **Choice: `<button type="button">` inside the `<th>`.** The `<th>` keeps its `onClick`. The button has **no** handler of its own, so its click bubbles to the `<th>` and `onSort` fires once.
- **Why not th-as-button:** `role="button"` on the `<th>` replaces its `columnheader` role. `DataTable.test.tsx:37,40,60,66,68` query `getByRole("columnheader")`, and `:60` clicks the `<th>` itself. Th-as-button, or moving `onClick` to the button, breaks those tests. That is stop condition 3.
- **Enter/Space:** a native button turns both keys into a `click`, and the click bubbles to the `<th>` as before. There is **no explicit `onKeyDown` and no explicit `preventDefault`**. A focused native button already consumes Space, so the page does not scroll. Adding `preventDefault` on Space keydown can suppress the button's own activation. Adding an `onKeyDown` that calls `onSort` would fire it twice. AC-102 says "(`preventDefault`)" in parentheses, so I'm asking for a ruling (C-5).
- **Rendered only when `onSort` is set.** No `onSort` means no button, no `tabIndex` and no `role`: today's markup exactly. Summary (`OwedBookScreen.tsx:251`) and Audit (`AuditScreen.tsx:85`) pass no `onSort`, so they are the non-focusable negative control.
- `aria-sort` logic is untouched: `ascending`/`descending` on the sorted column, absent otherwise. The button styling is a reset (`inherit` font, transparent background) plus a `focus-visible` ring.
- **Mobile card mode (`:119-166`) is not touched.** It has no headers. A test asserts `datatable-mobile` contains no `button`/`[tabindex]`.

### AuthedShell drawer (`src/components/layout/AuthedShell.tsx:45-117`): manual trap, not `inert`

- **Choice: manual focus trap**, as a React `onKeyDown` on the drawer panel.
- **Why not `inert`:**
  - (1) jsdom 26.1.0 has no `inert` implementation (`grep -rl inert node_modules/jsdom/lib` → 0). Containment would be untestable in jest. Browsers do support it (Chrome 102, Firefox 112, Safari 15.5).
  - (2) Resize hazard: the drawer is `lg:hidden`/`xl:hidden`. If you open it and widen the window, the drawer disappears but `inert` would stay on the page, leaving the **whole desktop page dead**. A trap scoped to the drawer panel does nothing when focus is not inside it.
  - (3) It keeps the negative control trivial: nothing ever touches the desktop rail.
- **Focus in:** an effect on `drawerOpen === true` focuses the first focusable in `sidebar-drawer`, which is the Close button (`:105`).
- **Containment:** on Tab, compute focusables in the panel at keydown time. Shift-Tab on the first → last, Tab on the last → first, with `preventDefault`. If `activeElement` is not inside the panel (for example a Radix Select portal), do nothing.
- **Escape:** the existing document listener (`:48-50`) is **byte-identical**. The body-scroll lock (`:52,55`) is unchanged.
- **Focus return (stored trigger ref):** `triggerRef = useRef<HTMLButtonElement>(null)` on the native trigger `<button>` (`:65`, not a `ui/*` primitive). When the drawer closes (Escape, backdrop, Close, route change, Apply), an effect does `if (triggerRef.current?.isConnected) triggerRef.current.focus()`. It only runs on the open→closed transition, never on mount, so there is no focus move on first render.

### MultiSelect (`src/components/common/MultiSelect.tsx`)

- **Focus in:** the search `Input` already has `autoFocus` (`:97`). React 19 focuses it on mount. That stays unchanged and gets a test.
- **Containment:** `onKeyDown` on the panel (`multiselect-panel`). Tab wraps between the first focusable (search input) and the last (last checkbox, or Clear all). It calls `preventDefault` + `stopPropagation`, so the drawer's trap never double-handles.
- **Focus return:** `triggerRef` on `<Button>`. `src/components/ui/button.tsx:43` is `React.forwardRef`, so passing `ref` is existing API. **No `ui/*` change.**
  - Escape → `setOpen(false)` + `triggerRef.current.focus()`.
  - Click-outside still closes via the untouched `mousedown` listener (`:29-36,40`). It does **not** pull focus back; the user clicked elsewhere.
- **Nested Escape order (picker first, then drawer):**
  - The picker's Escape moves from the document listener (`:37-39,41,44`) to the container's React `onKeyDown`. When the picker is open, it calls **both** `e.stopPropagation()` **and** `e.nativeEvent.stopImmediatePropagation()`.
  - The second call matters. The App Router hydrates with the **root = `document`** (`node_modules/next/dist/client/app-index.js:32` `const appElement = document`, `:293 hydrateRoot(appElement…)`). React's root listener and AuthedShell's Escape listener therefore sit on the **same node**, and plain `stopPropagation` does not stop the second one.
  - React registers its root listener at hydrate time, before any effect adds AuthedShell's, so `stopImmediatePropagation` blocks the drawer's handler.
  - In jest, the root is a `<div>`, so a naive test passes either way. The test therefore also adds a native keydown listener to the render container after mount (the production shape) and asserts that it does **not** fire.
  - Result: the drawer's Escape handler is **not touched**.
  - Fallback, if you'd rather have order-independence: a one-line `if (e.defaultPrevented) return;` in AuthedShell's handler (`:49`) plus `preventDefault` in the picker. That touches the drawer handler, so it's your call (C-6).

## b. Cache header design (S2)

- **Pattern: `source: "/((?!_next/static/).*)"`**. This is a one-token change at `next.config.js:16`. Header values, `images.*` and `output` stay byte-identical.
  - I recommend it over the brief's example `/((?!_next/static|_next/image|icon.png).*)`, which excludes more than the AC asks for.
  - `icon.png` is **not hashed**. If it's excluded, Next would serve it with its own long cache, and a changed icon would go stale.
  - `/_next/image` is unused (Cloudinary `remotePatterns` only), so excluding it gains nothing.
  - The brief's pattern also over-matches `/_next/staticky` (no trailing slash) and treats the `.` in `icon.png` as a regex wildcard.
- **Route-matching rule relied on:** Next compiles `source` with its bundled path-to-regexp. An unnamed group `(…)` is passed through as a raw regex, so a negative lookahead is legal. This is the same mechanism `/(.*)` already uses.
- **Proof on Next 16.2.12's own code** (run against `node_modules`, config untouched):

  - `loadCustomRoutes` → accepted (1 header rule).
